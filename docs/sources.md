## Access and review

The ST product and documentation endpoints returned HTTP 567 from this environment. The official eStore returned HTML for all three target device listings. [ST website terms](https://www.st.com/content/st_com/en/about/terms-of-use.html) restrict automated access. The ST Adapter uses reviewed local evidence, and the scheduled collector does not connect to ST websites. The [ST eStore robots.txt](https://estore.st.com/robots.txt) did not disallow the observed paths, but robots rules do not grant permission to automate access.

The CMSIS collector checks robots.txt before reading each origin, including download redirects. Keil returned 404 for robots.txt. Its Azure Blob distribution hosts returned 400 for the root-level path outside any container. These responses indicate missing policies. Explicit denials, rate limits and an unreachable robots endpoint stop collection. Requests use an identifying user agent, run sequentially with a one-second minimum gap, have a 20-second timeout per HTTP request and retry transient failures once. The collector deduplicates identical requests within a run and retains the last accepted observation time when pack evidence is unchanged.

To update ST evidence, review each product listing and document through an allowed channel. Save the official eStore markup locally as `st-store-<base-model-lowercase>.html` for each of the three scoped devices. Review the document version and applicability against the PDF title or supported-device table, update `data/seeds/st-documents.json` and its review timestamp, then run `pnpm import:st <dir> <UTC ISO observation time>`. Run validation and open a PR. Product extracts and curated document evidence are separately timestamped. ST document dates were omitted where only an update label or a month was established. The family documentation page or eStore may use a different official URL alias than the product page or the PDSC. These aliases are tracked as evidence without inventing URL equivalence or revision dates.

## Microchip Product Data API

The [official API guide](https://www.microchip.com/designresources/PartnerDataExchange/ProductAPI-user-guide.html) documents `part`, `pagesize` and `pagenumber`. The collector requests 20 rows per page and verifies the reported page number, size, total, expected row count and absence of repeated order codes. The recorded probes yielded 15 rows for PIC16F18313, 32 for ATMEGA328P and 21 for ATSAMD21G18A. The 12 shipped codes are an explicitly scoped sample of these results. The AVR response also contained neighboring ATMEGA328PB and development-board records. The SAM response used `ATSAMD21G18` as the `base_part_number` for the selected `ATSAMD21G18A-*` order codes.

A source row must identify Microchip silicon, the exact `part_number`, the expected `base_part_number` and an official `product_url` for that code. Primary documents use the `datasheet_url` field. Secondary sheets use `secondary_datasheet_url` only when their scope has been confirmed. The AVR API includes the automotive sheet even for standard order codes. The catalog associates it with the two selected automotive codes only. Scope is stored per orderable part, and a document identity is deduplicated across parts.
